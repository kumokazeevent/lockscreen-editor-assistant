# ADR 0003：观察后台已有列表 JSON 捕获正文

状态：已实施于 0.14.2；历史决策日期待确认。

## 上下文

落地页抓取曾读到版权页脚或与记录错位的内容；后台页面已有列表 JSON 携带 `content`。扩展需要按内容 ID 把正文绑定到正确卡片，并尽量减少逐条网络请求。

## 考虑的选项

1. 在 `MAIN` world 观察页面已有 fetch/XHR JSON：复用后台已取到的数据，无额外逐条正文请求；但依赖站点响应结构，并触及页面网络 API 包装。
2. 每条记录单独抓取文章落地页：独立于列表响应；但更慢，可能受跨域、反爬、动态页面或版权页脚影响。
3. 只用原简介/原标题：实现简单；但有错位或信息不足时无法代表正文。

## 决策

`page-bridge.js` 于页面启动时观察 JSON，克隆响应而不改写它；通过同源 `postMessage` 提供内容 ID、标题、简介、正文给 `content.js`。捕获失败时，批次处理按文章页、原简介、原标题继续兜底。

## 原因

现有 `README.md` 和 0.14.2 迭代笔记明确记录了“已有列表数据包含正文、避免逐条请求”的目的。技术上，ID 绑定比仅凭标题或页面位置更能防止错位；克隆响应和失败捕获避免影响站点原有请求。具体为什么选择 fetch/XHR 包装而非其他站点 API 集成方式，原因待确认：由前代 Agent 决策。

## 影响

- 正面：正常批次正文读取更快，减少落地页依赖，正文与批次可一同导出。
- 负面：页面若改变响应字段或改用其他传输方式，会退回兜底链；桥的内存上限、响应遍历和消息来源必须持续测试。
